## The residual changed

Earlier Helix candidates paid for source rereading, interface discovery, skill
setup, generated command glue and repeated model segments. Those operations do
not appear in the nine candidate paths here. The model receives sufficient task
state, produces replacement Python source, and the caller stages, tests and
publishes it. This establishes a narrower observable boundary, not a causal
explanation of internal model reasoning.

The supplied implementations are tiny incorrect stubs, not large mostly-correct
files. Exact copying of unchanged source has little apparent surface on these
particular repairs. The candidate must supply substantial new program behavior.
Using an already-solved benchmark implementation as a caller template would
move the answer outside the model and contaminate the fresh coding comparison.

**INFERRED:** recurring orchestration is no longer the primary removable term
inside these candidate trajectories. An optimization that only removes another
tool result or continuation cannot help where neither exists. This does not
make memory/reducers useless on other workflows, or establish a universal cost
floor. It changes which experiments deserve another native call.

target leaves `0.25 × O₀ − R` for all other output **if R stayed fixed**. A
negative allowance rules out solving that trace by shortening visible output
alone. A positive allowance does not prove that the required code fits it.

## Research decisions

| Proposed next attack | Verdict on these traces | Evidence needed before inference |
|---|---|---|
| Another command reducer | DEFER | Identify nonzero candidate output from a command that actually reaches the model |
| ACK or continuation suppression | SATURATED HERE | Show a new semantically resolved model segment; all current candidates have one |
| Shorter final prose/schema | NO MATERIAL SURFACE | Current output is source only; required code cannot simply disappear |
| More generic memory or cold plans | DEFER | Demonstrate repeated evidence/procedure cost greater than admission and retrieval cost |
| Lossless reuse of existing code | CONDITIONAL | Show relevant exact code available before the new task, invalidate changed dependencies, charge lookup and selection |
| Caller-owned standard validation | HYPOTHESIS | Generic validator must predate task answers; model still judges adequacy; reject subtly wrong validators |
| Lower effort or suppressed semantic probes | REJECT AS TARGET FIX | Would change the capability/workflow constraint rather than meet it |
| Repeat unchanged candidates until a cheap sample appears | REJECT | Variability study would need prespecified repetitions and all attempts included |

The smallest plausible next coding boundary is **reuse of genuinely existing,
version-bound behavior**, with the model responsible only for changed semantics.
Use an ordinary repository with substantial existing correct code, not these
tiny stubs and not a library built from their solutions. Freeze available code
before revealing a changed requirement. The control must have the same code
available. Both arms retain ordinary tools, semantic review, fresh tests and
recovery. If the existing native control already reuses it efficiently, accept
the smaller measured opportunity rather than inflate the baseline.

Before paying for that pair, exercise the existing reuse/realization machinery
offline against: changed source after preparation; an omitted dependency; a
well-hashed implementation incompatible with the new requirement; changed
requirements after a formerly completed decision; and interrupted publication.
It must preserve exact evidence and return unresolved semantic obligations,
rather than treat hashes or an old PASS as sufficient authority. If any case
requires an additional model call merely to discover the Engine interface,
or if the visible source-reuse opportunity is negligible, stop that proposal.

This is a **conditional research direction**, not a new installed mechanism or
prediction of 75/75. A materially different workload cannot retroactively repair
the failed three-task cells. The strong W50 and closed-retrieval results remain
separate evidence that whole-call removal works where transitions are actually
resolved. Novel coding retains model execution inside the Engine.
