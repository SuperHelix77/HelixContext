OBSERVED: six fresh Luna High streams completed, with ordinary tools and no model
retry. These known development tasks compare the default client base against the
compact V7 delegation base plus attached Helix Context. They exercise ordinary
execution outside the narrow W50 renderer. They do not constitute an isolated
Engine ablation, unseen holdout, or general intelligence/workflow certification.

## Behavioral checks and their actual scope

Code: both implementations pass the original four tests and a caller-run exact
largest-remainder oracle covering 4,433 combinations plus invalid-input cases.
Public parameter names are retained. Bound tests/settings hashes remain unchanged.
Source inspection confirms exact integer arithmetic, remainder/index tie breaking,
and Boolean rejection. This is not an exhaustive Python-object semantics proof.

Selection: both returned the full exact expected eligible set, total record count,
and job-0177 decision. Numeric strings were preserved; hostile note text did not
override the specified eligibility rule. The grader derives the answer from the
complete frozen records rather than trusting a model PASS statement.

Cold recovery: both actually accessed history.json and returned the original
selected label with exact code points/trailing whitespace, its UTF-8 base64, the
leading-zero sequence and evidence turn. This is a cold snapshot containing prior
events. It does **not** simulate 40 live model turns or establish compaction parity.

## Visible regressions and non-regressions

Coding Helix attempted skill activation despite caller-side native-thread
registration. The global runtime attempted to chmod its database and received a
PermissionError under the benchmark sandbox. Luna then searched `/Users/mert` for
the runtime, although it had already executed the known runtime path. This is a
workflow/scope concern beyond the functional grader. Both arms nevertheless
completed their authorized source edits and verification. Seven segments in each.
Do not weaken the sandbox or grant unrelated filesystem access to conceal this tax.

The common task prefix declared memory consultation and benchmark bookkeeping,
but did not explicitly state skill registration was complete as V5's prompt did.
This is a plausible integration defect, not evidence that activation always
recurs or that one wording change will fix all tasks.

Selection Helix did not visibly repeat activation. It loaded all records, generated
an extraction program, then performed further record verification: five segments
versus three in control. This evidence does not support attributing selection's
regression to skill setup. Data loading, generated procedure and verification are
distinct visible terms; hidden reasoning allocation remains unknown.

Cold Helix used four segments/two commands versus four/three in control. Fewer
commands did not reduce output. Both generated extraction/encoding work. Neither
exact retrieval correctness nor fewer tools is equivalent to economic success.

## Adjudication and next boundary

The V7 base/skill combination is **not admitted as a general Luna savings policy**.
Finite functional checks pass, but broad workflow parity is unproved and has the
scope concern above. The W50 caller-state mechanism remains a separate bounded
candidate at 75.66% output savings; this suite does not upgrade it to universal
98.53% input savings or finish the 80/80 objective.

Two next steps are justified by existing evidence, before another native sweep:
1. Ensure caller-completed registration is explicitly represented at the interface;
   do not make models rediscover already established runtime state.
2. For selection and coding, evaluate caller-owned realization against the actual
   generated extraction/application/test work. A kernel without those capabilities
   leaves mechanics model-owned. Preserve semantic selection, novel-check authority,
   exact evidence and re-entry on unexpected outcomes. Do not delete verification
   wholesale or invent a new source of token savings from overlapping categories.

These are investigations, not new claimed policies. Changing only output formatting
is not supported by the V5–V7 history. All three original models and broad
capability/long-horizon qualification remain in scope; only Luna ran in this suite.

After freezing these results, a research-only `engine/output/caller_registration.py`
adapter was added for the first item. It checks the active native-thread identity
and current attached-skill digest against the caller's registration receipt before
describing completed task-local registration. It does not attest global or future
compaction state, and adds no text on later turns or without an attached skill.
Six focused tests passed, including stale-skill and wrong-thread rejection. No
native run used this adapter; its behavioral benefit and admission remain untested.
