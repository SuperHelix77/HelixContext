## 1. Executive verdict

**INFERRED:** The highest-value next architectural change is **caller-owned,
exception-driven continuation after Astra’s semantic decision**. Astra chooses the
repair or next semantic action; Engine applies that exact decision, executes the
already-authorized mechanical checks, records state, and returns to Astra only for
an unresolved semantic obligation or exception. Scoped receipts make that handoff
inspectable. They are not a substitute for Astra judging whether the task was solved.

The council shrinks the search space to this execution boundary. It does not justify
building six opcodes, a new memory hierarchy, learned summaries, or a receipt framework
now. Prepared cognition and semantic deltas are possible later representations of
continuation state, not demonstrated efficiency mechanisms in current native runs.

**OBSERVED:** Sol V3’s caller-attached capability and zero-command selection succeeds
on a bounded fixture. Astra’s analogous assembly transfer is positive but below
80/80. On coding, supplying source and preflight did not remove inspection; input
regressed. **UNKNOWN:** whether inadequate receipt scope caused that behavior.

**CONDITIONAL:** Removing teaching/registration from the model’s responsibilities
is sensible, but “zero bootstrap alone fixes Astra” is not established. Both Sol V3
and Astra coding already registered the skill before inference. Astra had the
smaller explicit Helix wrapper. The missing boundary is more likely responsibility
for subsequent mechanics, not simply the number of bootstrap words.

**Decision:** audit survives; implementation remains deferred. One falsifier is
specified below. Sol stays frozen, Astra is primary, Luna follows only after a
surviving interface. This synthesis does not close the original benchmark matrix.

## 16. Semantic-delta assessment and invalidation semantics

**HYPOTHESIS:** `TaskState N` contains established facts with provenance, dependency
versions, completed actions, artifact identities, unresolved questions, constraints,
active procedures and invalidated assumptions. A delta references both its exact
base and new version; it never silently patches an arbitrary current state.

**CONDITIONAL design rules:**

- On a declared source/tool/config/schema/checker/policy/authority change, invalidate
  dependent derived claims transitively. Raw prior evidence remains accessible.
- A task-scope change invalidates sufficiency of a previously selected view, even
  if its bytes are unchanged. Preserve a source/epoch handle for late relevance.
- Unknown or missing dependencies mean “reuse not certified”; refresh/review or
  native execution. This is fail-closed reuse, not abandonment of the task.
- Reject out-of-order, duplicate-conflicting and wrong-base deltas. Publish a new
  authoritative state only after its required checks commit; retain failed evidence
  separately. A crash after an effect needs reconciliation, not blind replay.
- Expiry applies to time-dependent facts/permissions, not a universal arbitrary TTL.
- Stale semantic conclusions are visible historical claims marked stale, never
  permanent hidden truth. “No changes in watched files” does not prove no relevant
  world change.

Exact older evidence must be discoverable when relevance changes; a hash with no
available object is insufficient. Dependency tracking is not omniscience. Native
late-relevance and recovery tests remain required before any continuity claim.

## 17. Certified-receipt assessment and smallest useful statement

**HYPOTHESIS:** A scoped checked statement may let Astra avoid repeated mechanical
work. No current native experiment directly tests the council’s proposed certificate.
The earlier preflight proves an initial test execution, not that a later repair is
semantically adequate or that all future checks can be skipped.

A proposed compact resident receipt needs only:

| Resident field | Purpose |
|---|---|
| `state_transition` / operation ID | Exact base → resulting state, operation and status |
| `release_ref` | Bound policy, procedure, executor and checker versions in one immutable manifest |
| `input_root`, `dependency_root`, `output_root` | What was checked and what changed; versioned identities |
| `check_result` | Actual exit/status, passed/failed predicate identifiers; interrupted/pending distinguished |
| `unchecked` | Semantic adequacy, scope gaps and unresolved obligations explicitly retained |
| `evidence_ref` | Exact log/receipt/manifest recovery handle |

The expanded cold manifest retains the full dependency set, environments, hashes,
checker identity/verdict and per-step receipts. A reference may replace repeated
static fields only when its interpretation is already caller-bound and recoverable;
otherwise that schema becomes new bootstrap. No fixed “50-token receipt” is claimed.

**Trust boundary:** hashes bind bytes; an issuer/signature names an issuer; tests
establish only their executed predicates. None prove requirements were adequate,
the chosen operation was right, semantic interpretation was correct, or every
relevant dependency was declared. A configured checker validates mechanical claims;
Astra validates semantic sufficiency. Unknown checker or stale dependency invalidates
reuse. Correctly hashed semantic errors must remain detectable.

## 20. Best unified architecture candidate

**HYPOTHESIS — one boundary change, not a new framework:** a caller-owned semantic
continuation with scoped execution receipts and a minimal versioned task ledger.

| Owner | Concrete responsibility |
|---|---|
| Caller | Before inference, bind repo/worktree/version, task authority, release policy, available capabilities and evidence handles; perform authorized preflight and skill registration. Admit supported routes before preparation cost; otherwise native. Own orchestration and charge every call/recovery. |
| Helix Context | Small instruction bridge: use supplied state/evidence, preserve semantic responsibility, request exact missing evidence. No installation, registry operation, plan tutorial or duplicated ledger work. |
| Helix Engine | Apply exactly Astra’s selected action/patch; run approved tools/tests; mechanically validate roots, predicates and transactional publication; retain raw evidence; emit a scoped delta. No hidden semantic repair or model-generated summarization. |
| Persistent state | Initially only immutable task/authority roots, committed action IDs, artifact versions, open obligations and exact evidence references. Prepared semantic views remain optional, unqualified derived objects. |
| Astra sees | User task/constraints, exact relevant application evidence/diff, current state and changes, unchecked obligations, compact verified mechanical status, exact retrieval escape hatch. |
| Astra decides | Repair/selection meaning, missing information, adequacy of requirements/tests, whether to accept completion or which semantic repair is next. A needed patch may contain real code, not an artificial tiny selector. |
| Astra need not see routinely | Engine implementation, registration commands, copied payloads, hash transcription, repeated successful mechanical logs, generic plan/API setup, previously settled bookkeeping. |

After deterministic success, caller may mechanically render the already-authorized
result only if **all declared semantic obligations were explicitly discharged**.
Otherwise it returns the unresolved delta to Astra. It must not decide semantic
completion from exit zero. Unexpected failure, scope change, insufficient evidence
or unresolved adequacy wakes Astra with the smallest sufficient exact evidence.

Stale or unknown state invalidates reuse. Safe deterministic refresh can proceed
without inventing a semantic decision; consequential ambiguity returns to Astra.
Uncertain partial effects are reconciled before retry. Native fallback is selected
before execution or follows explicit recovery, never a silent second execution.

## 21. Cheapest architecture falsifier: one receipt challenge

**HYPOTHESIS test design only:** use a small new code-review/repair task with a public
contract and an externally supplied proposed patch. Every matching native/candidate
arm gets the **same patch and semantic evidence**. The caller must not secretly
provide a correct repair to only the Helix arm. “Review this proposed patch” is the
task; this pilot does not claim qualification for generating a novel repair unaided.

Three candidate receipt conditions:

- **Valid:** fresh roots; checked mechanical predicates genuinely passed; semantic
  adequacy remains Astra’s obligation. Desired: correct acceptance/repair decision
  without reconstructing the checker or repeating certified checks unnecessarily.
- **Stale dependency:** receipt binds an old requirement/source version; current
  version is observable. Mechanical gate rejects reuse and exposes the mismatch.
  Desired: no stale acceptance or effects; refresh/review according to the change.
- **Semantically wrong, correctly hashed:** patch/log hashes and limited mechanical
  tests are valid, but the patch violates an explicit semantic requirement outside
  those tests (for example, exact-int versus bool eligibility). Desired: Astra
  rejects/repairs it despite an authentic PASS for narrower predicates.

First audit the fixtures/checker with **zero model calls**: real execution must
produce the claimed mechanical outcomes, stale roots must be rejected, and the
independent semantic checker must distinguish the wrong patch. A stale-root unit
check alone does not require frontier inference. The native stale condition tests
Astra’s handling of the resulting changed semantic obligation, not its ability to
recompute a hash comparison the caller can do.

A false acceptance kills this release/interface immediately. Continued equivalent
mechanical reinspection plus cost regression weakens the claimed economic boundary;
it does not prove every possible receipt architecture impossible.
